# 01. 需求拆解与范围

## 1. “可测试的在线访问链接”是什么意思

面试官打开链接，不应安装 Node、克隆仓库或配置密钥，就能看到产品并操作主流程。对 Nucleus 来说，最小验收路径是：

1. 打开首页；
2. 输入“做一个任务清单”；
3. 等待 AI 规划和生成；
4. 在预览里新增、完成或删除任务；
5. 继续输入修改需求，生成 v2；
6. 打开版本历史，恢复 v1；
7. 点击发布，打开公开链接；
8. 下载 ZIP，看到三个真实源文件。

只有首页截图、Figma 稿、录屏或写死的演示动画，都不满足这个要求。

## 2. “实际可用，而不仅是 PoC”怎么判断

PoC 只证明一条技术路线可能成立；Demo 需要把主链路闭环。可以用下面的对比判断：

| 维度 | PoC 常见状态 | 本项目交付状态 |
|---|---|---|
| 输入 | 固定 Prompt | 用户可输入任意合理前端需求 |
| 模型 | 假数据或写死结果 | OpenCode Go 真实请求 |
| 生成物 | 截图或一段字符串 | HTML/CSS/JS 三个文件 |
| 运行 | 不可点击 | sandbox iframe 中实际运行 |
| 迭代 | 只能生成一次 | 带当前文件继续修改 |
| 数据 | 刷新即丢 | D1 保存项目和版本 |
| 失败 | 白屏 | 错误事件、提示、重试/修复 |
| 分享 | 无 | 公开 slug 页面 |
| 交付 | 无源代码 | ZIP 下载和公开 GitHub |

“实际可用”不等于“功能无限”。MVP 可以范围很窄，但承诺的范围必须真的工作。

## 3. 为什么没有复刻完整 Atoms

完整 AI 应用构建平台通常还包括：

- 任意 npm 依赖安装；
- 服务端代码和数据库自动生成；
- 容器或 WebContainer 隔离执行；
- 登录、团队、计费、权限；
- 多模型路由、队列和取消；
- 自动测试、截图比较和自修复；
- 自定义域名、日志、审计和后台管理。

这些不是一道短周期笔试能够稳定交付的范围。我们选择“无需构建的三文件前端应用”作为清晰边界，原因是：

- 不需要在服务端执行模型生成的任意代码；
- 不需要安装不受信任的依赖；
- 首次预览快；
- 能覆盖表单、看板、计时器、仪表盘、小游戏等常见 Demo；
- 可以把时间投入到版本、发布、错误处理和在线部署。

这是工程取舍，不是偷工减料。优秀的答辩应该主动说出边界和原因。

## 4. 功能优先级是怎么排的

### P0：没有它就不成立

- 创建项目；
- 真实调用模型；
- 生成完整三文件；
- 可交互预览；
- 云端保存；
- 公网部署。

### P1：证明不是一次性玩具

- 流式进度；
- 基于当前版本继续修改；
- 全量快照与恢复；
- 公开分享；
- ZIP 导出；
- 错误反馈。

### P2：产品化加分

- 登录和私有项目；
- 生成取消；
- 任务队列；
- 分级限额；
- 自动可访问性检查；
- 多模型选择。

笔试先完成 P0，再完成最能证明工程能力的 P1。不要在 P0 未闭环时花两天做动画。

## 5. 非功能需求

除了“有哪些按钮”，还要定义这些要求：

- 安全：密钥只在服务端；生成代码不得获得父页面权限；
- 稳定：模型空返回和漏文件时有恢复策略；
- 性能：完整生成目标 25–60 秒，过程必须有反馈；
- 成本：匿名访客每小时限制生成次数；
- 可维护：类型共享、数据访问集中、模型协议集中；
- 可交付：测试、构建、README、演示路径和公开源码齐全。

## 6. Definition of Done（完成定义）

一个功能只有同时满足以下条件才算完成：

- 主路径可以由用户操作成功；
- 失败时有可理解的提示；
- 刷新或重新打开后数据行为符合设计；
- 相关测试、类型检查和构建通过；
- 不泄露密钥或用户标识；
- 文档说明已更新；
- 在线环境实际验证过，而不只是在本地通过。

## 7. 当前明确限制

- 只生成浏览器端 HTML/CSS/JS；
- 不支持任意 npm 包和后端生成；
- 预览内 `localStorage` 是内存兼容层，刷新预览会丢；
- 公开链接靠不可预测 slug 分享，不是权限系统；
- 一个生成请求可能占用几十秒；
- 限流是轻量保护，不是完整反滥用平台。

面试时坦白限制不会扣分；说不清限制才会让人怀疑工程判断。
