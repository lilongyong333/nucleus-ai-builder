# 11. 零基础继续开发路线与练习

## 1. 先学什么，不要先学什么

推荐顺序：

1. HTML/CSS/JavaScript 基础；
2. HTTP 和 JSON；
3. TypeScript 类型；
4. React state/effect；
5. Git commit/branch；
6. API route 与数据库；
7. 流式协议；
8. 模型与安全边界；
9. 部署和监控。

不要一开始钻研框架内部的 RSC、Vite Environment API 或分布式数据库一致性。先能沿着一次请求找到每个文件。

## 2. 七天学习计划

### 第 1 天：会运行和观察

- 本地启动；
- 用浏览器 Network 看 `/api/projects`；
- 修改首页一句文案；
- 运行 lint/typecheck；
- 创建第一个本地 commit。

完成标准：你能解释“浏览器、API、D1、模型”各在哪里。

### 第 2 天：理解 React 工作台

- 找到 `project`、`generating` 和 `timeline`；
- 改一个 Agent 的显示颜色；
- 给 toast 显示时间改成 6 秒；
- 理解为什么 `startedRef` 防重复。

完成标准：你能说出 state 变化如何引起页面变化。

### 第 3 天：理解 API 和 D1

- 阅读项目创建路由；
- 画出四张表；
- 给项目增加一个可选 `description`（练习分支，不急着上线）；
- 同步修改 schema、migration、类型和 API。

完成标准：你知道数据库字段变化为什么不是只改一个文件。

### 第 4 天：理解模型协议

- 手工写一份合法 path code fence；
- 用测试喂给 parser；
- 写一个“多余文件应被忽略”的测试；
- 调整 Planner features 最大数量，观察 UI。

完成标准：你能解释为什么不用大 JSON。

### 第 5 天：理解预览安全

- 在生成 JS 里制造一个错误；
- 观察错误桥；
- 尝试 localStorage，理解 shim 生命周期；
- 阅读 iframe sandbox 各权限。

完成标准：你能解释为什么不加 `allow-same-origin`。

### 第 6 天：GitHub 与 PR

- 从 main 创建分支；
- 完成一个小功能；
- 写有 Summary/Verification/Risk 的 Draft PR；
- 自己在 Files changed 页面做一轮 review。

完成标准：主分支没有未经审查的临时代码。

### 第 7 天：部署与演示

- 跑完整四项检查；
- 按 smoke checklist 验证线上；
- 录制 90 秒无剪辑主流程；
- 练习回答本手册最后一章的问题。

完成标准：不用照稿也能讲清一个请求的完整链路。

## 3. 由易到难的功能练习

### L1：低风险 UI

- 增加空项目提示；
- 记住工作台上次打开的 tab；
- 给版本抽屉增加文件大小显示；
- 改善手机端布局。

成功率预估：理解基本 React 后约 85%–95%。

### L2：简单全栈

- 给项目加删除接口和二次确认；
- 给发布增加“取消发布”；
- 最近项目支持标题搜索；
- 导出的 README 增加生成时间和模型。

成功率预估：理解 API/D1 后约 70%–85%。

### L3：中等工程

- 增加生成取消；
- 把版本发布固定到 versionId；
- 加 GitHub Actions CI；
- 给 API 写集成测试；
- 把 rate limit 配置化。

成功率预估：需要处理并发/部署，约 55%–75%。

### L4：高难产品化

- 登录和项目所有权；
- 多模型切换与成本统计；
- 任务队列和后台生成；
- Playwright 自动点击和自修复；
- CSP/网络代理；
- 团队空间与权限。

成功率取决于外部服务和经验，零基础一次独立完成通常低于 50%，应拆成多个里程碑。

### L5：完整 Atoms 类平台

- npm/多文件项目；
- WebContainer 或服务端容器；
- 后端与数据库自动生成；
- 可观测性、计费、配额、审核、团队；
- 大规模并发和可靠发布。

这是团队级长期产品，不适合作为“再加一个功能”。需要安全、平台、前后端和运维共同投入。

## 4. 推荐的第一个真实改动：取消发布

按企业方式拆解：

1. 需求：已发布项目可撤下，旧链接返回 404；
2. API：`DELETE /api/projects/:id/publish`；
3. 数据：将 slug 置空；
4. UI：已发布时显示“取消发布”，需要确认；
5. 测试：发布成功、取消成功、旧 slug 404、重复取消幂等；
6. 安全：未来登录后必须校验项目所有者；
7. 回滚：重新发布会产生新 slug 还是复用旧 slug，需要产品先决定。

看起来是一个按钮，实际上涉及产品语义、API、数据库、测试和权限。这就是全栈开发。

## 5. 每次改代码的检查模板

```text
需求：我要改变什么用户行为？
范围：哪些文件应该变化，哪些不应该？
数据：是否新增/修改字段？旧数据怎么办？
API：请求/响应和错误码是否变化？
安全：权限、secret、用户输入、模型输出有什么风险？
测试：至少哪条自动测试和哪条手工路径？
部署：需要新变量或 migration 吗？
回滚：如何恢复到变更前？
文档：README/API/运维说明是否要更新？
```

## 6. 看不懂代码时怎么问 AI

差的问题：

```text
帮我解释整个项目。
```

更好的问题：

```text
只解释 components/workbench.tsx 中 runGenerate：
1. 输入和输出是什么；
2. buffer 为什么需要保留最后一段；
3. 哪三种失败会进入 catch；
4. 不改代码，先给我一张时序图。
```

要求 AI 引用具体文件/行、给验证方法、说出不确定性。不要复制一大段改动后只看“页面没报错”。

## 7. 如何判断自己真的学会了

不用看文档，能回答：

- Key 为什么不会到浏览器；
- 创建项目和生成为什么是两个请求；
- NDJSON 为什么需要 buffer；
- 首次漏文件和迭代漏文件为何处理不同；
- 版本恢复为什么不删除新版本；
- iframe 为什么没有同源权限；
- GitHub 和线上站点为什么是两个系统；
- 线上 200 但页面报生成失败，可能在哪一层；
- 如何在不破坏 main 的情况下提交改动。

能讲明白并亲手完成一个 L2 功能，就已经不是“只会运行别人代码”。
