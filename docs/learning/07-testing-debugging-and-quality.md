# 07. 测试、排错与质量

## 1. 五层验证

只看页面“好像能打开”不够。本项目使用四层验证：

| 层 | 命令/方法 | 主要发现什么 |
|---|---|---|
| 单元测试 | `pnpm test` | 解析、文件合并、预览组装 |
| 静态检查 | `pnpm lint`、`pnpm exec tsc --noEmit` | 代码规范、类型错误 |
| 生产构建 | `pnpm build` | 构建插件、Worker 兼容和产物问题 |
| 浏览器 E2E | `pnpm test:e2e` | 首页、流式 UI、账号中心、断流恢复 |
| 生产验收 | 登录浏览器/API 实测 | 密钥、D1、身份、模型、部署和真实交互 |

任何一层通过，都不能代替其他层。

## 2. 当前验证命令

```powershell
pnpm test
pnpm lint
pnpm exec tsc --noEmit
pnpm build
pnpm test:e2e
```

提交前运行全部五项。GitHub Actions 会在干净 Linux 环境安装 Chromium 后重复执行，防止“只在我的 Windows 上能跑”。

## 3. 已有单元测试覆盖什么

当前 30 个 Vitest 分布在 9 个文件：

| 测试文件 | 覆盖重点 |
|---|---|
| `parser.test.ts` | path code fence、增量合并、返回文件集合 |
| `runtime.test.ts` | 三文件组装、标签转义、缺文件拒绝、启动/错误桥 |
| `quality.test.ts` | 完整应用、语法错误、假交互、危险 AST、文本误报 |
| `session.test.ts` | visitor Cookie 复用、畸形替换、Set-Cookie 边界 |
| `identity.test.ts` | Sites 受信身份、不完整头降为匿名 |
| `model-gateway.test.ts` | 成功、503、超时、401、取消、空回复、调用/Token 预算 |
| `planner.test.ts` | 结构化计划上限和迭代摘要 |
| `usage.test.ts` | OpenAI usage 归一化与多调用累加 |
| `generate-route.test.ts` | 路由失败事件、Run 指标和终态持久化 |

4 个 Chromium E2E 覆盖：创建并打开工作台、流式 review/complete、登录账号详细链接、服务端生成断流恢复且零重复 POST。

## 4. 为什么测试要有独立 Vite 配置

Vinext 主 `vite.config.ts` 会加载 Cloudflare 插件和 Worker 环境。Vitest 如果直接复用它，可能在跑两个纯函数测试时启动不必要的 runtime 或产生兼容错误。

因此使用 `vitest.config.ts`：

- 只配置测试需要的别名和环境；
- 不加载 Cloudflare Worker 插件；
- 测试更快，失败原因更清晰。

原则：测试环境应尽量小，但不能小到与真实逻辑完全不同。

## 5. 线上 E2E 验收清单

每次正式版本至少手动跑一次：

- [ ] 首页返回 200，主要文案和样式正常；
- [ ] 创建项目返回项目 ID；
- [ ] 首次生成持续收到 NDJSON 事件；
- [ ] 最终收到 `complete`，状态 `ready`；
- [ ] HTML/CSS/JS 都非空；
- [ ] 预览中至少一个主交互可用；
- [ ] 修改需求生成 v2；
- [ ] 恢复 v1，再恢复 v2；
- [ ] 发布后公开页返回 200；
- [ ] 下载 ZIP 包含三个文件；
- [ ] 超限后返回 429；
- [ ] 浏览器控制台无主应用致命错误。

已经在线验证复杂面试看板、BudgetLens、面试清单和习惯打卡器，不是只测试固定 seed 页面。复杂看板还实际执行了新增、搜索、两次流转和统计更新。

## 6. 实际问题 1：pnpm 阻止原生构建脚本

### 症状

安装后 `esbuild` 或 `workerd` 没有正确构建，开发/构建命令失败。

### 原因

新版 pnpm 默认对依赖安装脚本更谨慎。一些工具确实需要安装期脚本准备二进制。

### 处理

在 `pnpm-workspace.yaml` 中精确允许需要的包，而不是允许所有依赖脚本。

### 学到什么

依赖安装脚本有供应链风险；白名单应最小化并进入代码审查。

## 7. 实际问题 2：旧构建类型污染 TypeScript

### 症状

切换构建方案后，`tsc` 报错指向已经不用的 `.next` 生成类型。

### 原因

旧产物仍在 TypeScript include 范围，编译器把过时生成文件当作当前事实。

### 处理

隔离旧产物到 `.artifacts`，并让 lint/版本控制忽略构建目录。

### 学到什么

生成产物不是源代码。换框架或构建器后先清理/隔离缓存，再判断是否是真代码错误。

## 8. 实际问题 3：大 JSON 输出损坏

### 症状

`JSON.parse` 抛出 `Unterminated string`。

### 原因

模型生成的代码包含大量需要二次转义的字符，长输出中更容易少一个引号或反斜杠。

### 处理

把协议改为 path-labeled Markdown code fences，解析文件边界，不再解析巨型代码 JSON。

### 学到什么

不要只靠更强 Prompt 对抗结构脆弱性；改变传输协议通常更有效。

## 9. 实际问题 4：增量回复只有一个文件

### 症状

“增加深色模式”只返回 CSS/JS，校验认为 HTML 缺失。

### 原因

模型把请求理解为补丁，而系统最初要求每次都全量输出。

### 处理

首次生成仍要求全量；迭代时将新文件覆盖到当前快照上。

### 学到什么

协议要区分 create 和 update 语义。

## 10. 实际问题 5：sandbox localStorage 异常

### 症状

生成应用调用 `localStorage` 时抛 SecurityError，预览功能中断。

### 原因

未授予 `allow-same-origin` 的 sandbox iframe 使用不透明 origin。

### 处理

保留安全隔离，注入页面生命周期内的内存 storage shim。

### 学到什么

遇到安全限制时，不要第一反应是扩大权限；先寻找最小兼容方案。

## 11. 实际问题 6：模型 HTTP 成功但内容为空

### 症状

接口返回 200，但 `message.content` 是空字符串。

### 原因

模型/提供商偶发行为，或者结果落在推理字段。

### 处理

一次自动重试；在推理字段确实包含完整协议标记时容错提取。

### 学到什么

HTTP 成功不代表业务成功。外部 API 返回必须做结构和内容校验。

## 12. 实际问题 7：首轮生成漏 CSS

### 症状

HTML 和 JS 存在，但第一次没有 `styles.css`，无法形成有效 v1。

### 处理

解析部分文件，计算缺失集合，只让模型补缺失文件，再合并校验。

### 学到什么

可靠 AI 系统不是“Prompt 一发就完事”，而是“生成—检测—定向修复—再校验”。

## 13. 实际问题 8：公网额度可能被刷

### 症状

任何匿名用户都可触发付费模型，公开链接等于公开消费入口。

### 处理

增加 D1 原子计数、匿名哈希指纹、每小时 8 次和 429 响应。

### 学到什么

上线前必须考虑成本攻击；“没有用户数据”不等于“没有安全风险”。

## 14. 实际问题 9：同项目并发和旧请求晚到

### 症状

两个标签页同时生成，较慢旧请求可能覆盖较新的结果，或创建相同版本号。

### 处理

数据库 `generation_id` 单写者租约、409 冲突、AbortSignal、取消 API、终止后拒绝写事件/版本，以及版本号唯一索引。

### 学到什么

按钮 disabled 只是体验，不是并发控制。正确性必须由服务端数据库边界保证。

## 15. 实际问题 10：浏览器网络流断开，服务端仍在生成

### 症状

工作台显示 network error，D1 却仍是 `generating`；刷新又可能重复提交。

### 处理

8 秒心跳、禁缓冲响应头、断流后 GET 项目并轮询、终态同步、`generating` 项目零重复 POST、始终可取消。

### 回归

Playwright 首次返回 running，之后返回 ready，断言 UI 自动显示 v1 且 `/api/generate` POST 次数为 0。

## 16. 实际问题 11：小模型探针和真实代码负载结论相反

Qwen 的规划探针较快，但复杂三文件代码生成超过边缘窗口；GLM 同题在确定性 Iris 后 21 秒完成。最终用真实应用基准决定 GLM -> Qwen，而不是看模型列表或单条短回复。

## 17. 实际问题 12：登录成功，但账号页的链接点不动

### 症状

`/account` 能显示姓名、邮箱和三个云端项目，说明身份和 D1 都正常；“新建应用”和“打开工作台”的 `href` 也正确，但点击后 URL 仍停在 `/account`。

### 证据

生产浏览器 Console 出现 Vinext RSC prefetch/navigation 的 `TypeError: ... is not a function`。这证明故障位于客户端路由运行时，不是登录回调、项目所有权或数据库。

### 处理

关键跨页面入口改用普通 `<a href>` 或 `window.location.assign()`，强制浏览器发起完整文档请求，继续携带同域身份会话并绕开有缺陷的客户端 RSC 路由。首页锚点等同页跳转仍保持原方式。

### 回归

Playwright 不再只检查 `href`，而是实际点击“打开工作台 → 返回首页 → 项目中心 → 新建应用”，逐步断言 URL 与目标页面内容。这个案例说明：静态属性正确不等于用户路径可用。

## 18. 排错顺序

遇到失败时按层定位：

1. 浏览器 Network：请求是否发出，状态码是什么；
2. Response：普通 JSON 还是 NDJSON，最后一个事件是什么；
3. 主页面 Console：React 或流解析是否报错；
4. iframe 错误条：是生成应用自身错误吗；
5. Worker 日志：模型/D1/绑定是否异常；
6. 模型原始响应：协议、截断、漏文件还是空内容；
7. D1：项目状态、版本记录是否一致。

不要一看到页面不对就立刻改 CSS。先确定故障在哪一层。

## 19. 企业级下一步测试

- API contract test：验证所有状态码和错误结构；
- 数据库 integration test：在临时 D1 上跑 CRUD/并发；
- 云端生成物 Playwright：对每个新 Version 自动点击、填写表单、保存截图和控制台；
- 模型 eval：固定需求集评估完整率、交互率、延迟和成本；
- 安全测试：恶意 HTML、超长输出、外部请求、弹窗和 CPU 消耗；
- 视觉回归：核心工作台截图比较；
- 负载测试：并发生成、D1 锁争用和模型超时。
